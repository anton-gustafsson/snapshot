A service, not a widget

Remember what a view
looked like.

capture(el, id) turns any DOM element into a stored image, keyed however you want, on whatever backend you want. <snapshot-nav-list> is one thing you can point it at — not a requirement. Use the service on its own and render the result anywhere. 

npm install @anton-gustafsson/snapshot-core
  1. 01

    Capture on the way out

    Call capture(el, id) when the user leaves a view — any element, any framework.

  2. 02

    It's stored, keyed by id

    IndexedDB by default. Swap in your own backend so it follows the user across devices.

  3. 03

    Show it wherever

    get(id) returns the image URL — an <img>, a <snapshot-nav-list> tile, anything.

The service

No UI required.

This is the whole surface area. No component to mount, no framework to adopt — just a function that captures an element and a function that reads it back. 

import { getDefaultSnapshotService } from '@anton-gustafsson/snapshot-core';

const snapshots = getDefaultSnapshotService();

// capture anything — a report panel, a canvas, a form preview
const panel = document.querySelector('#quarterly-report');
await snapshots.capture(panel, 'q3-report');

// read it back wherever — a table cell, an email preview, your own component
const url = await snapshots.get('q3-report');
thumbnailImg.src = url;

// a second dimension on the same id — one capture per theme
await snapshots.capture(panel, 'q3-report', { variant: 'dark' });
const dark = await snapshots.get('q3-report', { variant: 'dark' });

// one batched read for a whole list, then let the tiles paint from it
await snapshots.prefetch(['q3-report', 'q2-report', 'q1-report']);

// drop thumbnails whose entity is gone
await snapshots.prune(['q3-report', 'q2-report']);

// react to updates from any tab, any origin-mate that shares your storage
snapshots.subscribe((id, url, variant) => updateThumbnail(id, url, variant));

Storage is pluggable

Ship it as-is for a single-device tool, or point it at your own backend so thumbnails follow the user across machines. 

import { SnapshotService, type SnapshotKey, type SnapshotStorage } from '@anton-gustafsson/snapshot-core';

class ApiSnapshotStorage implements SnapshotStorage {
  async save(blob: Blob, key: SnapshotKey) {
    const body = new FormData();
    body.append('file', blob, `${key.key}.webp`);
    const res = await fetch(`/api/snapshots/${key.key}`, { method: 'POST', body });
    return (await res.json()).url;
  }
  load(key: SnapshotKey) {
    return fetch(`/api/snapshots/${key.key}`)
      .then((r) => (r.ok ? r.json().then((j) => j.url) : null));
  }
  async remove(key: SnapshotKey) {
    await fetch(`/api/snapshots/${key.key}`, { method: 'DELETE' });
  }
}

export const snapshots = new SnapshotService({
  storage: new ApiSnapshotStorage(),
});

Every method takes a SnapshotKey: { id, variant?, key } — the bare id as you passed it, the variant if the call carried one, and the fully-qualified key (prefix and variant already folded in) that's safe to use verbatim. Optional loadMany(keys) and keys() unlock one round-trip per list and prune(); optional attach(service) hands your storage the service so it can publish() a late-arriving image with no wiring on your side.

Storage recipes

Three common configurations. Live, working versions of all three are in the gallery app — /icon-grid etc. use the default, and /sqlite / /sqlite-only cover the other two end to end.

IndexedDB only (the default)

No storage option needed — this is what you get for free.

import { SnapshotService } from '@anton-gustafsson/snapshot-core';

export const snapshots = new SnapshotService();
// same as: new SnapshotService({ storage: new IndexedDbSnapshotStorage() })

A real database only, no fallback

Point storage straight at it. Every get() is a real query — no client-side cache in front of it, so a slow backend means a slow (but honest) spinner. 

import { SnapshotService, type SnapshotKey, type SnapshotStorage } from '@anton-gustafsson/snapshot-core';

class SqlSnapshotStorage implements SnapshotStorage {
  async save(blob: Blob, key: SnapshotKey) { /* INSERT/UPSERT, return a displayable URL */ }
  async load(key: SnapshotKey) { /* SELECT, return a displayable URL or null */ }
  async remove(key: SnapshotKey) { /* DELETE */ }
}

export const snapshots = new SnapshotService({
  storage: new SqlSnapshotStorage(),
});

The gallery's /sqlite-only page is exactly this, with sql.js (real SQLite, compiled to WASM) standing in for the database — see apps/gallery/src/sqlite-storage.ts.

Backing snapshots with a server

The common case for a real app, and the one you shouldn't hand-roll: CachedSnapshotStorage puts a local IndexedDB cache in front of your API. You write the two calls only you can write; it owns the caching policy. 

import { CachedSnapshotStorage, SnapshotService } from '@anton-gustafsson/snapshot-core';

export const snapshots = new SnapshotService({
  keyPrefix: 'reports:',
  encode: { type: 'image/webp', quality: 0.8, maxEdge: 640 },
  storage: new CachedSnapshotStorage({
    remote: {
      // null (not a rejection) for "nobody has captured this yet" — a 404 included
      load: async (id) => {
        const res = await fetch(`/api/snapshots/${id}`);
        if (res.status === 404) return null;
        if (!res.ok) throw Object.assign(new Error(res.statusText), { status: res.status });
        return res.blob();
      },
      save: async (blob, id) => {
        const body = new FormData();
        body.append('file', blob, `${id}.webp`);
        await fetch(`/api/snapshots/${id}`, { method: 'PUT', body });
      },
    },
    // upload a small copy; the local cache keeps the full capture
    uploadEncode: { type: 'image/webp', quality: 0.8, maxEdge: 480 },
    maxBytes: 256 * 1024,          // mirrors the server's own cap
    onError: (err, key, op) => {   // filter the routine failures yourself
      if ((err as { status?: number }).status !== 403) console.warn(op, key.key, err);
    },
  }),
});

Why the defaults are what they are — these five behaviours are the reason this isn't consumer code:

  1. Local first, revalidate behind it. load() returns the cached image immediately and reads the server in the background, publishing the result only if it actually differs. A cold miss awaits the server and returns its URL directly.
  2. A server answer of "nothing" never evicts a local capture. A 404 is the normal answer for a snapshot nobody has uploaded yet — not a reason to throw away the one this browser just took.
  3. A failed read never evicts either. Rejections go to onError and the local copy stands, so thumbnails still work offline.
  4. Saves don't wait for the upload. The local write is awaited (you get a displayable URL); the PUT is fired and forgotten, so a slow or refused upload can't delay a navigation.
  5. Freshness is the HTTP cache's job. ETag + Cache-Control: no-cache — no version bookkeeping in the library.

Live version with simulated latency, a 404 and a 403: the gallery's /remote-storage page. /sqlite is the same recipe over real SQLite (sql.js, compiled to WASM) — see apps/gallery/src/sqlite-storage.ts.

Capturing safely in a framework

Capture the frame the user is about to leave, not the one that's already gone: flush pending renders, wait one animation frame, then check the element is still attached. In Angular that whole dance is injectSnapshotCapture(). Do not wait on whenStable() inside a canDeactivate guard — the router holds a pending task for the entire navigation, so it resolves only after the view is destroyed, and html2canvas then fails with "Unable to find element in cloned iframe". A detached element rejects with SnapshotDetachedElementError rather than storing a blank thumbnail over a good one.

Angular

npm install @anton-gustafsson/snapshot-angular
// main.ts — one place to configure the service; nothing binds [snapshotService]
import { provideSnapshot } from '@anton-gustafsson/snapshot-angular';

bootstrapApplication(App, {
  providers: [provideSnapshot({ keyPrefix: 'reports:', encode: { type: 'image/webp', maxEdge: 640 } })],
});
import { SnapshotNavListComponent, injectSnapshotCapture, type NavItem } from '@anton-gustafsson/snapshot-angular';

interface Report { owner: string }

@Component({
  selector: 'app-root',
  imports: [SnapshotNavListComponent],
  template: `
    <ngx-snapshot-nav-list
      [items]="items"
      [variantKey]="theme()"
      (select)="onSelect($event)"
      (edit)="onEdit($event)" />
  `,
})
export class AppComponent {
  // signal inputs/outputs, zoneless-safe, no [snapshotService] binding needed
  private capture = injectSnapshotCapture();

  items: NavItem<Report>[] = [
    { id: 'sales', label: 'Sales', icon: '📈', editable: true, data: { owner: 'me' } },
  ];

  // the whole item arrives — no lookup by id
  onSelect(item: NavItem<Report>) { /* ... */ }
  onEdit(item: NavItem<Report>) { /* ... */ }

  // ticks, waits a frame, re-checks the element; resolves null instead of throwing
  save(el: HTMLElement, id: string) {
    return this.capture(el, id, { variant: this.theme() });
  }
}

The Angular package re-exports the core surface (NavItem, SnapshotService, CachedSnapshotStorage, …), so a consumer imports from one package. Peer requirement: @angular/core >= 19.

Scoping the service (lazy routes)

provideSnapshot() returns EnvironmentProviders — it only works at an environment injector location: bootstrapApplication()'s providers, or a route's own providers array. Not a @Component's providers — that's an element injector, and Angular rejects makeEnvironmentProviders() there.

Put it on a lazy route instead of the app root when a feature's snapshots (and its keyPrefix) should live and die with that feature, not with the whole app: 

// app.routes.ts
import { Routes } from '@angular/router';
import { provideSnapshot, CachedSnapshotStorage } from '@anton-gustafsson/snapshot-angular';

export const routes: Routes = [
  {
    path: 'reports',
    loadComponent: () => import('./reports/reports.component').then((m) => m.ReportsComponent),
    providers: [
      provideSnapshot({
        keyPrefix: 'reports:',
        storage: new CachedSnapshotStorage({ /* ... */ }),
      }),
    ],
  },
];

Created once, the first time the route loads. Destroyed — releasing the BroadcastChannel and freeing the keyPrefix claim — when the route's injector is destroyed (deactivated, and RouteReuseStrategy isn't keeping it alive), so re-entering the route later constructs a fresh instance with no "keyPrefix already in use" warning. Skip provideSnapshot() entirely and SNAPSHOT_SERVICE falls back to the app-wide default (providedIn: 'root') — fine for a single feature, but without the keyPrefix isolation and per-feature encode/storage a lazy scope buys you.
